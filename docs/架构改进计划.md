## 第二轮实施记录（2026-10-13）

- **收拢修改入口。** 画布脚本动作直接使用公共事务记录历史，原生随机变种和随机偏移也在事务中执行。注册表的标量、字段、向量、结构体修改接入同一入口；向量元素追加和元素类型更新在同一事务内完成。
- **地图只作投影。** 删除主窗体内所有 `SyncGrid` 调用及事后补记历史入口。BTL 保存、两种 JSON 导出、工作文档快照和 JSON 查看只读文档。随机变种只修改目标位段，偏移只修改目标成员，保留重叠/离图部队、重复建筑和额外属性尾部。
- **保留交互语义。** 新增 `BeginHistoryGroup()`，一次刷图或偏移拖动合为一次撤销；每次移动立即提交，失败只撤销该次移动。松手、失去捕获、窗口失焦和撤销等中断路径结束分组并停止落笔。空操作不增加历史。
- **回滚后重建引用。** 原生批次、注册表操作失败后重新投影；撤销后显式使注册表树失效，避免后续继续修改旧节点。
- **兼容边界。** `FrontNav.SyncGrid` 和 `EditSession.RecordExternalChange` 暂保留给旧调用方及兼容测试，当前编辑器不再调用。`MapCell` 仍持有文档节点引用，单向使用由编辑入口约定保证，尚未增加不可变节点或只读包装。界面刷新仍由提交回调协调，尚未改为通用变更订阅。

验证：核心及脚本测试 127 项通过（本轮新增 4 项）；XML UI 检查包含新增的 `MapTransactionChecks`，验证真实鼠标拖动、捕获丢失、拖动中撤销、原生/注册表失败回滚，以及过期画布不影响 BTL 和两种 JSON 导出。注册表只读与来源检查通过。大地图验证沿用 242×121、461 个部队、827 个事件样本，渲染对照、异步打开、撤销/重做及 128 MiB 历史预算检查通过，保留 22 帧。性能命令沿用第一轮入口，标签为 `architecture-round2`；包源漏洞元数据获取仍有 `NU1900` 提示。尚未在游戏内验证本轮导出。

## 第三轮实施记录（2026-10-13）

- **扩大公共字段覆盖。** 部队基础字段、行为/将领/特种配置，以及建筑/工事映射已集中到 `EditorLayout/fields/unit.json` 和 `site.json`。XML 表单、地图外部队表单及列表列使用字段 ID；Lua 对象、身份修改和创建使用同一目录，迁移范围内不再重复声明基础结构体布局。

- **工作文档保留定义来源。** 成功提交时保存参与使用的目录快照、指纹和字段 ID；读取、整体无变化与失败不新增记录。记录随 JSON、克隆、撤销/重做和外层事务回滚恢复。游戏 BTL 与字段名/ID JSON 不携带这些编辑器元数据。
- **明确剩余边界。** 字段目录还未覆盖全部地形、势力等功能；低层原始路径修改不会自动记录字段来源。字段使用记录不是逐字段操作日志。影响比对已有 API，尚无迁移向导和影响报告界面；底层布局与特殊编码扩展仍等待实际新格式需求。

## 1. 改进目标

继续沿用“通用结构树 + 可替换的格式解释 + Lua 操作 + XML 界面”的路线，让编辑器能够跟随 `.btl` 格式研究持续演进。

下一轮改进重点是降低三类变化的成本：

| 研究进展 | 希望达到的效果 |
| --- | --- |
| 发现一个普通字段的用途 | 补充公共字段定义和界面即可，不必重复修改多处路径、类型和位段 |
| 推翻已有字段类型或布局判断 | 能确定旧文档使用的解释版本，明确重新读取或迁移，并检查差异 |
| 发现新的打包结构或文件变体 | 有清楚的编解码扩展位置，不让特殊规则逐渐散入界面和通用读写器 |

衡量改进的标准是：一次研究结论变化涉及的修改位置更少、验证更清楚、旧功能更容易保持。类的数量、接口的数量或配置化比例不作为目标。

## 2. 当前基础与需要保留的设计

以下能力已经存在，后续在其基础上改进：

- **通用中间表示。** `BtlFront` 按字段 ID 保存 table，节点携带类型与结构体布局；缺失字段和显式零值有所区分。适合表达物理结构已知、业务用途尚未确定的数据。
- **原件与解释分离。** `BtlBinaryInspection` 保留原字节及其指纹，重新解释不会替换编辑文档；可以查看未知槽和解析失败的位置。
- **读档诊断参与导出决策。** `FrontSession` 已根据 `Ok` 和 `HasUnresolvedData` 限制编辑与重建导出。下一步是将该约束落实到可复用的核心入口，而不是重新实现一遍 UI 提示。
- **分层脚本接口。** 数字路径用于探索，`game` 对象封装已有认识，`editor.tool` 提供批量工具和参数声明。
- **事务与热加载保护。** 脚本失败已有文档、剪贴板及状态回滚；布局完整创建成功后才替换当前页面。
- **现有验证与性能优化。** 已有字段存在性、结构体布局、局部修改、脚本回滚、原始查看和 UI 测试；深拷贝、刷新缓存及大地图渲染也已有优化和测量。

早期问题记录见 [设计问题与改进清单](设计问题与改进清单.md)。其中部分描述对应改造前状态；本计划以当前实现为起点，不直接继承旧条目的未完成状态。既有性能依据见 [性能优化说明](性能优化说明.md)。

## 3. 设计原则

1. **继续保留弱类型树和原始路径入口。** 暂时未知的字段不必先获得一个确定的业务名称，也不强制进入固定游戏实体类。
2. **区分物理结构、业务含义和研究可信度。** 确认一个值占两字节，不代表已经确认它是生命值；暂定业务规则不能成为强制拒绝导出的依据。
3. **原始文件始终是独立证据。** 编辑、撤销、布局热加载都不替换原件；尝试其他 schema 不自动改变当前文档。
4. **一个知识点有明确的权威定义位置。** 基础物理布局归 schema；语义映射及位段归公共字段定义；特殊编码归对应编解码器。
5. **文档是唯一可提交的数据状态。** 画布、表单和注册表提供投影或操作入口，保存不负责隐式补交界面缓存。
6. **渐进兼容。** 先增加新入口、迁移一个完整场景并验证，再扩大范围；旧 Lua API、数字绑定和旧 Front JSON 要有明确的兼容路径。

不知道字段用途与不知道字段编码必须分开处理。原字节可以保留用于研究，但未知块可能包含偏移引用，不能承诺把它搬进重建文件就能无损保留。普通重建仍以足够明确的物理结构为前提。

## 4. 目标职责划分

以下是职责目标，具体类名可以在实现时调整，不要求立即新增工程。

| 位置 | 主要职责 | 需要逐步收拢的内容 |
| --- | --- | --- |
| `BtlCore` | Front 树、格式解释上下文、结构校验、编解码、无 UI 的编辑会话基础 | schema 实例及缓存、结构化诊断、事务和文档历史基础 |
| `BtlScriptHost` | Lua 运行环境、具名对象适配、字段目录加载、工具和布局协议 | 让脚本写操作加入公共事务，向 Lua 和界面提供同一份字段描述 |
| `BtldMapEditor` | 选择、交互、地图绘制、控件生成和诊断展示 | 将格式知识和直接数据写入移出控件；画布只投影当前文档 |
| `schema` / `EditorLayout` | 可维护的物理定义、语义映射、业务动作和呈现 | 记录定义版本、来源与兼容要求，支持原子替换有效配置 |

依赖方向继续保持：编辑器依赖宿主和核心，宿主依赖核心。核心不依赖 WinForms 或 MoonSharp；脚本回滚等附加行为通过无 UI 的协作接口接入。

## 5. 实施顺序

优先级表示先后顺序，不表示已经确认存在对应的数据损坏故障。

| 阶段 | 优先级 | 主要交付 | 进入下一步的条件 |
| --- | --- | --- | --- |
| A：建立迁移基线 | 先做 | 代表性样例和已有行为清单 | 明确什么必须保持，记录已知差异 |
| B：固定解释上下文与导出契约 | 高 | 文档会话使用明确 schema；公共导出保留诊断与严格校验 | 两份解释互不影响，未决状态不会在入口之间丢失 |
| C：集中字段定义 | 高 | 部队字段试点，XML 和 Lua 共用描述 | 修改一份定义即可同步影响两类入口 |
| D：统一修改与投影 | 高 | 会话负责提交、回滚、历史和变更通知 | 保存不再回写画布；已迁移入口行为一致 |
| E：整理底层扩展点 | 按需要 | 共享布局规则，必要时增加特殊编码注册 | 有具体新格式需求和回归样例支撑 |

建议先完成 A、B 的最小版本，再做 C 的部队试点。C 的定义盘点与 D 的写入口盘点可以同时准备，但避免在同一批改动中全面重写字段访问和状态管理。

### A. 建立迁移基线

**工作内容**

- 从现有测试中挑出迁移必须维持的行为，优先补充有缺口的场景，不重新搭建另一套测试框架。
- 准备小型合成样例：缺失与显式零、可选子表、位段、重叠及离图部队、额外地形属性、行为树、未知或损坏槽。
- 选择少量代表性原版样本，记录样本指纹、当前解释版本、预期诊断及导出状态。
- 保留一组当前性能基线，后续在相同样本和运行条件下比较。

**验收标准**

- 能分别验证无修改往返、单字段修改、失败回滚、撤销重做和重新解释。
- 比较同时关注字段存在性、向量顺序、非目标数据以及预期字节差异；不能只检查“写完能读”。
- 原版样本缺失时明确报告未执行相应检查，不能用合成样例通过代替真实样本结果。

### B. 固定解释上下文与导出契约

**要解决的问题**

编辑读写目前共同使用全局 `SoftSchema`，而原始查看已可以独立指定 schema。文档自身没有携带解释来源；核心写入器也不能仅凭一棵树知道其读入过程是否完整。

**工作内容**

1. 引入轻量格式上下文，持有一次解释使用的 schema 实例及其缓存。先为读写、JSON 转换和节点创建增加显式上下文入口；旧入口暂时适配默认上下文。
2. 在会话或工作文档元数据中记录 schema 内容指纹、研究修订、公共字段和脚本包版本、使用的特殊编码版本，以及可获得的原文件指纹。Front JSON 的格式版本与这些版本分开。
3. 将诊断整理为“代码、路径、类别、严重度、对重建的影响”。导出资格不再依赖提示文字中是否包含某个中文词。
4. 普通导出统一检查来源中的未决状态及当前树的可编码性。缺少必要布局、发生截断或需要用空值替代原值时，不以普通成功结果落盘。已知合法兼容情况通过明确规则区分。
5. 对新建文档和 JSON 导入也做当前结构校验。旧 JSON 缺少研究元数据时标为来源未知，不直接当作损坏，也不凭空补成某个已验证版本。
6. 定义解释优先级：原字节是证据，固定 schema 是基础，研究性的类型或布局覆盖必须显式记录。冲突时报告具体位置，不能由某个读写步骤静默选一边。

**研究与升级方式**

- 试验其他 schema 时继续创建独立解释视图。
- 将新解释用于编辑，应明确选择“从原文件重建工作文档”或执行有定义的迁移；已有修改不能自动套到新布局。
- 普通导出入口走完整上下文。直接从树构建字节的底层接口可保留为实验能力，但不能被上层当作安全导出的替代入口。
- 元数据的首选承载是工作文档/会话及实验记录，不随意增加游戏 `.btl` 字段。JSON 元数据应有向后兼容方案。

**验收标准**

- 同一进程内，用两份 schema 解释、编辑和构建相同样本时互不影响。
- 文档及节点创建始终使用其固定上下文，不受后来加载的全局配置影响。
- UI、脚本批处理及命令行采用公共导出服务时，得到一致的允许/拒绝决定和诊断。
- 已确认正常样本仍可导出；未决文件不会因只传递 `Document` 而丢掉限制。
- 单独证明“二进制可编码”与“符合游戏语义”的校验结果；未经证实的游戏规则只提供研究提示。

### C. 集中字段定义，先迁移部队字段

**要解决的问题**

例如生命值的路径、类型在 Lua 与 XML 中重复出现；经验和编制的位段也需要同步维护。更新字段理解时，容易只改一处。

**建议方案**

在 `EditorLayout` 中增加可由 C# 读取的声明式字段目录，首版可采用 JSON，由宿主加载后同时提供给 Lua 对象层和 XML 绑定。不要让 XML 为取得字段元数据而执行任意业务脚本。以下标识和属性只是拟定协议，尚不是现有 API。

| 描述项 | 示例或用途 |
| --- | --- |
| 稳定语义标识 | `unit.hp`、`unit.level`，与中文显示名称分离 |
| 对象锚点与相对位置 | 相对于部队对象定位成员，避免每个使用者重复根路径 |
| 物理类型来源 | 优先从会话 schema 解析；临时覆盖需要注明来源并校验冲突 |
| 位段信息 | 位移、宽度及底层存储字段，确保修改时保留其他位 |
| 存在性与创建策略 | 缺失、显式零、可选对象启用，以及何时允许补建父节点 |
| 研究说明 | 物理类型和业务含义各自的确认程度、证据或试验编号 |

建议先迁移 `hp`、`max_hp`、`level`、`stack`，再选一个可选配置验证“未写入”和“启用对象”的处理。XML 引用语义标识并描述展示，Lua 的 `game` 属性使用同一描述执行读写。

集合增删、扩图重映射、行为树操作等复杂行为继续由代码或 Lua 函数表达；字段目录无需成为通用业务语言。地形紧凑排列等算法应集中到一个公共实现，不能只将重复常量搬进配置后仍保留多份算法。

**兼容与加载**

- 保留旧 XML 数字 `bind` 和研究用底层 API；新绑定不要求一次迁移全部页面。
- 旧脚本 API 2 和已有 `game` 属性保持兼容。确需改语义时记录适用版本和迁移方法。
- 新字段目录、XML 和 Lua 作为一份有效配置验证后再切换；冲突或加载失败保留旧配置。
- 已迁移字段同时出现旧、新绑定时明确报错，避免优先级取决于加载顺序。
- 对保留的直接路径实现增加针对性一致性检查，列清尚未迁移的位置。

**验收标准**

- 普通工具和 XML 对同一字段获得一致的值、存在性和写入行为。
- 调整一处位段定义后，两类入口同步变化，邻接位保持不变。
- 仅补充字段语义或改显示名称，不要求修改核心编解码器。
- 读取字段不补建节点；可选字段的空值语义、64 位整数精度和旧 JSON 布局兼容不退化。

### D. 统一修改入口，使地图成为文档投影

**要解决的问题**

`MapCell` 同时包含暂存值和文档节点引用，保存及历史记录前依赖 `SyncGrid`。脚本有事务，界面又自行追加历史与刷新；操作越来越多时，同步顺序难以持续保证。

**工作内容**

1. 提取无 UI 的编辑会话，先统一“开始操作、成功提交、失败恢复、文档替换通知”。核心会话只管理通用文档职责。
2. 让脚本宿主加入该事务，继续负责自身状态、剪贴板、运行时恢复和句柄失效。嵌套调用加入同一外层操作，不重复拍快照或重复生成撤销帧。
3. 迁移一个普通 XML 修改和一个脚本工具，证明成功、无变化和失败三种情况的行为一致。
4. 再迁移画布中的地形修改、随机变种与偏移、粘贴和注册表修改；列清仍直接改文档或格子缓存的入口。
5. 让画布从文档生成读取投影。手势预览可以临时存在，但真实提交必须进入会话；先完成或取消手势再执行保存。
6. 全部相关入口迁移后，移除保存和历史记录中的隐式 `SyncGrid`。迁移期间保留兼容同步，但标明所属旧入口，不能到处兜底回写。

**事务与历史的约定**

- 一次普通动作或批量工具成功且文档改变，产生一个撤销帧；无变化不增加帧；失败恢复操作前状态。
- 动作失败仍恢复文档、脚本剪贴板和 `editor.state`。用户撤销与失败回滚分开定义：首版保持现有撤销文档的语义，不悄悄扩大到所有工具状态。
- 文档替换、回滚或撤销后，脚本句柄与界面缓存失效并重新定位；原始二进制查看对象不变。
- 通知先采用“文档已变化”的粗粒度形式；只有实际刷新成本需要时才增加细粒度变更集。
- 保留直接深拷贝与既有历史预算。连续绘制的提交粒度先明确并验证，再考虑快照合并或差量优化。

**验收标准**

- 脚本修改后切页、保存、撤销和重做，不会被旧地图缓存覆盖。
- 非目标字段、向量顺序、重叠及离图部队、额外属性、非地图事件均被保留。
- Lua、XML、注册表和地图操作使用一致的提交与导出约束。
- 保存只读取当前已提交文档；失败操作不会留下部分修改或多余撤销帧。
- 已有脚本预算、只读刷新、句柄寿命和热加载行为保持有效。

### E. 根据新发现整理底层扩展点

这一阶段由实际研究需求触发，不作为前三项完成的前置条件。

- **布局计算：** 新增嵌套 struct、对齐或其他物理类型支持时，优先共用类型描述、偏移计算和字节访问，保留原始查看与编辑读取不同的容错策略。查看支持不等于编辑重建支持，需分别声明能力。
- **特殊编码：** 目前保留独立 `PackedJsonStream`。出现第二种打包格式或同一编码的多个版本时，再增加小型注册机制，描述作用字段、识别条件、版本和编解码过程。
- **游戏特定规则：** Root 特殊写入顺序、特定字段的解码路由等逐步归入格式配置。不要未经实验就清除当前兼容规则。
- **原始载荷：** 对已明确属于独立字节载荷、且确认可保留的未修改内容，可研究复用原载荷；这不推广为任意未知 FlatBuffers 块都能直接搬移。
- **其他前端：** 当前计划先覆盖这三个工程，不同时重写 Verifier 或移动端。公共接口稳定后再决定复用范围。

验收以新增格式的具体样例为准：同一结构在查看、编辑和重建中的解释一致，或明确给出不支持诊断；增加编码不要求修改普通页面。

## 6. 将研究证据纳入日常改进

每次修改 schema、公共字段定义或特殊编码，随改动保存一份简短研究记录：样本指纹、旧解释、新解释、依据、影响范围、验证结果，以及尚未确认的部分。物理类型与业务含义的证据分开记录。

| 验证层次 | 检查内容 | 不能替代的验证 |
| --- | --- | --- |
| 结构检查 | 原始槽、类型、布局、缺省和偏移是否符合预期 | 不证明字段业务用途 |
| 编辑契约 | 目标修改生效，其他数据保留，回滚和撤销一致 | 不证明游戏接受所有组合 |
| 游戏试验 | 代表性样本的实际加载和单变量修改效果 | 不把少量成功样本推广成所有版本的定论 |

优先扩展现有测试入口，按改动范围执行，不要求每次文档或局部调整都跑完整性能实验：

- `tests/FrontEdit.Tests`：核心、脚本、字段绑定及结构契约。
- `tests/XmlUi.Smoke`：页面、工具、热加载、提交和撤销。
- `tests/Registry.Smoke`：原始查看、重新解释和只读边界。
- `tests/Smoke`：合成数据和原版样本往返。
- `tests/Performance.Smoke`：涉及读取、投影、事务和渲染成本时，对照既有基线。

共享底层布局实现后，多条读取路径可能共享同一种错误，因此仍保留手工构造的字节预期、原始偏移断言和游戏试验。无修改往返可以继续比较字节；因已知规范化而不同的结果，应记录差异依据，不能只凭树比较通过就忽略。

## 7. 建议拆成的交付单元

每项应保持可构建、可验证；前一项通过后再扩大迁移范围。

| 顺序 | 交付单元 | 完成标志 |
| --- | --- | --- |
| 1 | 基线样例与行为清单 | 现有兼容约束和已知差异有记录 |
| 2 | 显式格式上下文 | 读写可使用两份互不影响的 schema，旧接口仍可用 |
| 3 | 结构化诊断及公共导出 | 来源限制与当前结构校验贯穿普通导出入口 |
| 4 | 部队字段目录试点 | 普通字段、位段、可选配置各有完整迁移案例 |
| 5 | 公共事务入口试点 | XML 修改与脚本工具共用提交和历史协调 |
| 6 | 画布及注册表迁移 | 直接写入口被收拢，保存取消隐式同步 |
| 7 | 扩展字段迁移范围 | 按地形、势力、关卡逐步推进，持续减少重复知识 |
| 8 | 带具体样例的底层扩展 | 根据新发现整理布局或特殊编码，而非预先泛化 |

研究版本记录和验证说明随各项一起补充，不放到所有重构完成之后。首轮完成标准是前三个核心边界——解释上下文、字段定义、修改入口——各自出现一个经过验证的完整用例，而不是一次性迁完全部文件。

## 8. 主要风险与控制方式

| 风险 | 控制方式 |
| --- | --- |
| 新字段目录变成第二份 schema | 物理类型与布局优先从 schema 派生；覆盖必须显式记录和校验 |
| 新旧接口长期并存且结果漂移 | 按功能维护迁移清单，保留一致性测试，避免新增功能继续复制旧定义 |
| 严格校验误拦合法原版数据 | 区分结构错误、已确认兼容规则和业务猜测，用代表性原版样本验证 |
| 事务合并改变工具行为 | 固定无变化、失败、批次、嵌套调用和用户撤销的语义后再迁移 |
| schema 升级错误解释已有修改 | 固定会话版本，显式重新读取或迁移，禁止静默重新解释 |
| 为扩展性引入过多基础设施 | 先做部队字段与两种写入口试点；有第二个真实需求再提炼通用扩展点 |
