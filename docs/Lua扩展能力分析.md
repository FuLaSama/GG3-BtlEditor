# Lua 脚本写法与格式扩展能力分析

日期：2026-10-13  
范围：`EditorLayout/scripts`、`BtlScriptHost` 的脚本接口，以及与扩展边界有关的 `BtlCore` 读写流程。  
状态：第 1–6 节保留两次改进前的静态分析记录；已实施第一轮格式扩展与第二轮对象层整理，实施和验证记录见第 7–8 节。原分析本身没有新增运行测试。

项目背景：编辑器面向仍在研究中的游戏私有 `.btl` 格式。评价扩展性时，既要考虑是否容易编写工具，也要考虑新字段、新布局和新打包格式能否通过扩展接入。

## 1. 总体判断

当前 Lua 具有通用的数据操作能力，编写普通工具比较容易；公共对象库内部仍有维护成本，格式解析层还没有完整的 Lua 扩展入口。

两次分析关注的层次不同：

| 分析 | 关注的问题 | 结论 |
| --- | --- | --- |
| 第一次：脚本写法与可维护性 | 新增工具、对象属性、复杂操作是否方便 | 普通工具轻便；公共模块组装、格式细节收拢和复杂操作约定需要改善 |
| 第二次：普遍性与纯 Lua 扩展 | 新研究成果能否不改 C#、只加 Lua 就完整支持 | 常规字段和位段大多可行；读取前的类型声明、通用编解码注册仍有缺口 |

需要区分两个目标：

- **不修改 C#、不重新编译编辑器**：允许修改 Lua、`.fbs`、字段目录或布局 XML。现有机制已能覆盖不少扩展。
- **只新增或修改 Lua**：连读取所需的类型说明、特殊编码接入也由脚本完成。现状还不能完整满足。

## 2. 第一次分析：脚本写法与可维护性

### 2.1 现有优点

1. **工具声明集中。** `editor.tool` 把标题、作用范围、参数与执行函数放在一起；宿主负责参数检查和整批事务。恢复生命的核心操作是 `unit:heal()`，带参数工具通常也不需要另写 XML 窗口。用户工具目录支持自动发现和重新加载。
2. **具名对象便于理解和复用。** `unit.hp`、`unit.general`、`game.events` 隔离了部分数字路径。页面动作与独立工具共享适配层，格式解释变化时可以减少修改位置。
3. **保留底层研究入口。** 未封装的字段仍可通过数字路径和 JSON 接口访问，不必等待全部内容都进入 `game` 对象。
4. **局部修改与失败恢复有基础。** 普通属性更新不要求重建整个对象，失败由宿主回滚；未知成员可在局部修改中保留。操作手册已说明空值、数组、遍历和对象寿命等约定。

### 2.2 不同扩展的成本

| 扩展任务 | 当前成本与涉及位置 |
| --- | --- |
| 批量修改生命、经验、金币或地形 | 较低，通常一个 Lua 工具文件即可 |
| 给现有具名对象增加普通属性 | 中等，通常补字段定义和 Lua 属性映射；需要展示时再补界面 |
| 调整已接入字段目录的路径 | 较低，使用这些属性的工具通常不用改；类型或布局变化仍需核对 schema 与重新读取 |
| 新增复杂对象或集合操作 | 需要熟悉公共工厂、初始化、关联数据和对象寿命约定 |
| 新增工具作用范围或专用参数控件 | 目前还受 C# 宿主和界面支持范围限制 |

这里的“补字段定义和属性映射”指正式接入具名对象；临时研究工具可以直接用 `editor.data`，并非所有字段操作都必须先改公共库。

### 2.3 主要维护问题

**公共对象由多个文件依次补充、替换。**

`游戏对象.lua` 先定义集合，`业务对象.lua` 再替换部分部队、势力方法，地图模块继续向共享方法表添加功能。页面之间还通过 `write_unit_general` 等全局函数协作。XML 已明确加载顺序，但一个对象的最终行为需要跨文件追踪。

建议每种对象由一个明确模块负责构造和导出，公共工厂单独存放，跨模块依赖显式表达。已有对外 API 可以保留。工具和动作允许同名覆盖是现有扩展机制，整理时应保留有意覆盖的能力，并改善来源与冲突提示。

**复杂操作仍夹带部分物理格式知识。**

`地图操作.lua` 判断建筑和工事时仍直接使用数字路径，而普通事件对象已经接入字段目录。未来调整建筑结构解释时，普通属性访问与扩图判断可能不同步。

建议对象识别、字段定位和紧凑地形读写复用公共适配接口；扩图脚本主要表达坐标重映射、保留或删除对象等业务规则。普通业务脚本无需重复掌握底层排列方式。

**复杂脚本需要记住多种操作约定。**

- 对象属性写入直接影响文档；数组通常读取为副本，修改后需要整体赋回。
- `update` 表达局部更新；Lua 表不能保存值为 `nil` 的键，因此 `update {general=nil}` 不会删除配置，直接赋 `unit.general=nil` 才会删除。
- 普通遍历适合修改属性；批量删除需要倒序等明确策略，不能在固定数量的遍历中任意改变集合长度。
- 对象、句柄和迭代器只在当前调用中有效，跨调用应保存普通数据并重新定位。

这些约定已有文档，并非都需要改写。建议为常见易错操作增加辅助方法，例如按条件删除和明确清除可选配置，并补充供编辑器使用的类型注释、参数说明和返回值提示。

第一次分析原本建议按“模块归属整理 → 收拢格式细节 → 常用辅助方法与代码提示”推进。第二次分析明确了更高层的格式扩展目标，因此整体优先级调整见第 4 节。

## 3. 第二次分析：新字段和打包格式能否纯靠 Lua

### 3.1 当前能力边界

| 新发现或新增内容 | 纯 Lua 能力 | 条件与限制 |
| --- | --- | --- |
| 已正确读取的字段，刚研究出业务用途 | 可以 | 用数字路径访问，再封装为工具或具名接口 |
| `u16/u32` 中打包多个属性 | 可以 | 用位运算拆分、替换目标位段并保留其他位 |
| 普通表、数值、布尔、向量或显式布局的结构体 | 可以在内存中创建、修改 | 不代表再次打开文件时能正确识别；读取所需类型说明仍需配套 |
| 已正确读取为普通 `u8` 向量的新打包内容 | 有条件可以 | Lua 自行解码、修改、编码并写回；受现有运行预算和基础接口限制 |
| 字段在读取阶段被认错、猜测或跳过 | 不能仅靠现有 Lua 接口完整解决 | 需要修正解释并从原始文件重新读取；普通类型变化可能只需修改 `.fbs` |
| 一种新编码随打开自动解包、随保存自动打包 | 当前没有通用 Lua 注册入口 | 需要先为宿主和核心增加扩展接入机制 |

该表不是“所有 FlatBuffers 类型均已开放”的承诺。例如数字路径标量写入未开放普通字符串业务字段；完整 64 位整数已有精确字符串读写接口，但不能因此把普通 Lua 数字位运算视为任意 64 位编码的通用方案。

### 3.2 为什么数据操作通用，不等于文件格式扩展完整

目前流程是：

```text
二进制文件 → C# 按 schema 解析 → 内存数据树 → Lua 编辑 → C# 写回
```

`editor.data` 提供数字路径、显式标量类型、结构体布局、向量操作和精确整数接口，因此脚本并不受现有 `game.units` 等具名对象种类限制。

但 Lua 操作的是解析完成后的数据树。当前没有 Lua 接口让脚本在读取前登记新的物理字段类型，也没有从 Lua 接管原文件解析、重新解释并核销相关诊断的完整流程。公共字段目录的语义映射同样不能替代读取器需要的 schema。

没有类型提示时，读取器会启发式猜测并记录未决状态；写入器拒绝重建仍含未决源数据的文档。脚本后来给某个路径写入看似正确的值，不会自动证明原始内容已经完整解释，也不会消除这一限制。

因此，“能在内存里新建字段”和“新字段能完整经历打开、编辑、保存、再次打开”是两个验收层次。修改 `.fbs` 可能足以支持新的普通结构，无需改 C#，但这属于 Lua 加格式配置的扩展。

### 3.3 两种打包问题应分别处理

**整数位段打包：现有能力较通用。**

例如某个已正确读取的整数中新发现第 4～6 位表示一个属性，可以用 Lua 读取原值、替换目标位段、保留其他位后写回，无需添加 C# 业务代码。

**独立字节流编码：可以手工处理，缺少自动接入。**

若内容已经作为普通 `u8` 向量进入数据树，脚本可以完成：

```text
读取字节数组 → Lua 解包 → 修改 → Lua 打包 → 写回普通字节数组
```

这条路线可以实现新功能，但宿主不会自动把脚本登记为该字段的编解码器。脚本需要自行组织调用和对象表示。

现有国家行为树的流程是专门实现：`BtlToFront` 针对 `/10` 调用 `PackedJsonStream`，向量带上 `country_ai_bt` 编码标记，`FrontToBtl` 再调用对应编码器。Lua 可以通过 JSON 接口修改已经解出的内容，但目前不能注册另一个具有相同自动接入能力的新编码器。

## 4. 合并后的改进优先级

以下为建议，尚未实施，也不表示已经确定最终 API 名称或签名。

| 优先级 | 改进方向 | 要解决的问题 |
| --- | --- | --- |
| 优先 | 读取前的类型和布局声明入口 | 新字段、结构布局和向量类型能进入文件读取阶段；继续支持 `.fbs`，严格纯 Lua 则需等价注册能力 |
| 优先 | 通用编解码器注册 | 扩展提供适用条件、解码和编码逻辑，宿主负责接入读取、编辑与保存 |
| 配套 | 二进制操作基础接口 | 提供方便的字节缓冲区读写、大小端转换和精确数值处理，减少重复底层算法 |
| 后续 | 公共模块归属与复杂操作整理 | 降低多文件替换方法、共享全局变量和重复路径解释的维护成本 |
| 后续 | 辅助方法、类型注释和示例 | 降低遍历删除、可选配置、数组回写等场景的编写成本 |
| 按需 | 工具作用范围与参数控件注册 | 出现实际新目标或交互需求时扩展；现有 `stage/map` 工具可自行遍历处理许多场景 |

这次优先级调整的依据是：项目希望适配新研究成果，而不仅是为已经理解的结构增加批量操作。应先补齐决定扩展上限的入口，再完善脚本内部组织。

## 5. 后续设计需要保持的约束

- 类型、编码和脚本扩展应属于明确的解释上下文，并能记录版本；不能悄悄改变已打开文档所依据的解释。
- Lua 解码、编码产生的修改应继续参与公共事务、失败恢复和撤销，不能另建一份脱离文档管理的可写状态。
- 对已确认边界、独立存放的字节载荷，优先保留原始内容供未修改或无法识别时使用。含未知偏移引用的任意二进制块，不能承诺直接搬入重建文件就能无损保留。
- 保留未决数据诊断与导出约束。扩展应提供正确解释与验证，不能只提供清除错误标记的捷径。
- 不要求所有新功能都必须进入具名对象库；通用底层接口仍是研究和试验的重要入口。

未来验收应至少覆盖：只加脚本实现新的普通字段工具、位段更新保留邻位、独立字节流编解码往返，以及新类型声明在重新打开文件后仍生效。未识别或编码失败时应保留明确诊断；这些是后续验证目标，不是本次已通过的测试结果。

## 7. 第一轮格式扩展实施（2026-10-13）

已优先打通“只加 Lua 声明普通物理类型、操作独立字节载荷”的完整场景：

- `editor.format.schema` 接受 Lua 内的 `.fbs` 片段，表按显式字段 ID 合并，结构体整体声明布局。合并后形成独立上下文，不改变全局默认 schema；编辑器打开、JSON 打开和新建入口已使用该上下文。
- `editor.format.codec` 登记有版本的解码、编码函数，`format.read/write` 在工具和动作中调用。载荷保持普通 `u8` 向量，按需解码并显式写回，不自动扫描整个文件，保存也不执行 Lua。
- `editor.binary.create/read/write` 提供缓冲区、大小端、整数和浮点读写；完整 64 位整数使用字符串保持精度。
- 编解码回调共用脚本预算，并限制直接访问文档和状态；编码输出完整验证后才修改向量，支持事务回滚、撤销和重做。
- 成功修改记录载荷路径、编解码器版本和定义源文件指纹，随工作 JSON 与历史保存。类型声明变化需要重新打开关卡；已记录载荷的编解码器版本变化会提示不匹配。

接口和限制见 [Lua 格式扩展](../EditorLayout/格式扩展.md)，完整合成示例见 [research_packet.lua](../EditorLayout/examples/research_packet.lua)。示例未登记到自带布局，不会自动给真实关卡添加虚构字段。

第一轮结束时尚未实现：自动扫描并挂接解码视图、任意未知偏移块的重定位、通用压缩或字符编码库，以及第一次分析提出的全部模块整理。字段目录和 XML 页面不会由 Lua 类型声明自动生成。对象层整理的后续进展见第 8 节。

验证：解决方案 Release 构建通过，0 警告、0 错误；核心及脚本测试 148 项通过（本轮新增 16 项），覆盖独立解释、实际用户工具目录安装、二进制往返、大小端和精确整数、版本变化、纯回调约束、非法输出、超时与内外层回滚。XML UI 检查通过，新增真实编辑器流程验证异步打开、生成工具菜单、载荷修改、撤销/重做、保存及重读；既有二进制/JSON 往返检查通过。未进行游戏内验证。

## 8. 第二轮对象层整理（2026-10-14）

- **模块归属明确。** 公共工厂提取为 `editor.modules.objects`，部队、势力、事件、关卡和地图各自在 `scripts/objects` 中一次定义完整。默认值、增删关联规则通过构造选项表达，不再由后加载文件替换集合方法。对象方法统一采用普通 Lua 的 self 参数约定。
- **新增属性和对象有正式入口。** 集合支持加载阶段的 `define_field/define_method`；新集合通过公共工厂声明。`research_objects.lua` 同时示范物理类型声明、部队属性与方法、新研究集合及工具，未加入默认布局。
- **扩图复用公共解释。** Lua 只保留实体取舍和坐标规则，通过事件方法识别建筑、工事，并跟随字段目录覆盖。紧凑地形的投影、搬运和写回复用 `TerrainEdits`，保留完整结构布局、额外成员和未关联尾部。
- **常见操作可复用。** 普通集合新增 `all/each(predicate)/remove_where`；批量删除先筛选再倒序执行，复用集合关联清理规则。可选配置提供 `ensure/clear`，保留局部更新与整组删除的明确区别。
- **页面辅助函数集中。** 部队整份表单写入集中到 `unit/配置表单.lua`；部队、行为树页面使用显式模块接口，移除共享全局写入函数。地形层名由地图模块统一提供。
- **补充编写支持。** 新增对象/集合/工厂的类型注释和 `.luarc.json` 库路径配置。使用与迁移说明见 [Lua 对象扩展](../EditorLayout/对象扩展.md)，完整示例见 [research_objects.lua](../EditorLayout/examples/research_objects.lua)。手工列举内置脚本的外部宿主需按新的 `layout.xml` 调整依赖；公开的工具、动作、属性和冒号方法保持兼容。

## 9. FlexBuffers 研究接入与正确性修复（2026-10-15）
