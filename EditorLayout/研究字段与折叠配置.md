# 研究字段与折叠配置

本轮依据 `battle - 人工命名版.fbs` 的中文标注整理界面。界面使用短名称，说明放入悬停提示；原标注带星号、未知或未确认的内容保留不确定性提示。英文表名、旧 Lua 属性名并不作为字段含义的依据。

## 界面加载与性能

XML、字段名称目录和 Lua 在启动时加载；“重新加载布局”是明确点击才执行的开发入口，不监视文件变化。切换对象不读取 XML，也不销毁、重建属性页。打开文档时绑定一次该文档的格式解释；普通数据刷新不重复解析字段映射。

详情控件在第一次展开时建立，然后复用。切换地图格、势力或列表条目时，只把现有控件绑定到当前对象并更新值；未展开的深层配置等再次展开时才更新。可选配置的“未写／已写”通过复用同一组状态控件切换，新增或删除配置不要求重建整页。列表结构未改变时保留行和选择，只更新变化的文本。复用的编辑器始终根据当前绑定写入，不能沿用旧对象、旧向量或旧条目的引用。

一批更新完成后集中重绘，容器和列表启用双缓冲；保留有效的滚动位置、焦点和未改变输入框的光标位置。选择刷新与实际编辑仍然分开：切换对象不会生成事务或撤销记录。

本机同一合成样例中，展开部队详情及嵌套加成列表、连续切换 24 次对象，优化前平均约 608 毫秒，优化后约 11–20 毫秒；分配内存由约 217 MB 降至约 3.8 MB，切换期间没有控件创建或销毁。这是属性栏的特定测试场景，实际耗时还受地图规模、已展开项目及机器环境影响。

`tests/XmlUi.Smoke` 的 `SelectionPerformanceChecks` 同时验证控件和列表行复用、当前对象写入、嵌套条目选择、可选配置状态、折叠后重新绑定、焦点、滚动及撤销刷新。可用 `--selection-perf-only` 单独运行，结果保存在 `artifacts/selection-performance/after.json`。

## 从哪里修改

常用项目仍在原来的页面，复杂配置默认折叠。点击标题箭头展开，再次点击收起。折叠不写入文档，也不生成撤销记录；同一页面实例中，选中其他对象、刷新、撤销或重做会保留展开状态。重新加载布局或重启程序恢复 XML 的默认状态。

| 页面 | 补充的内容 |
| --- | --- |
| 部队 | 将领勋章；完整基础结构、国家兵种加成、动态状态、临时加成、击败奖励、行为树绑定和运行字节；部队组及战略驻军 |
| 建筑 | 地块名称、目标标记、着火状态、占领奖励；招募 AI、建筑加成、增援落点、建筑行为树、集团军设施；全部地标、省份和开放区域 |
| 势力 | 兵种科技、特种部队与招募冷却、卡牌状态、动态状态、AI 倾向、国家行为树、战略 AI 等 |
| 全局 | 文件版本、Lua 触发状态、增援队列、空中支援、待用卡牌、可购买增援、军需、已用奖章、玩家将领池；增援点附加参数 |
| 地形 | 默认地质 |
| 共用行为树 | 原有 FlexBuffers 编辑器继续使用，属性组和节点组可以折叠 |

部队详情优先跟随地图外列表选择；重新选择地图格后跟随地图选择。势力详情跟随势力列表。建筑详情跟随当前格的地块事件；没有事件时，可在“全部地标与省份 → 地块事件”中添加条目并设置地图格，或先使用原有添加建筑、工事按钮。

名称修正的例子：原“修饰势力”改为“士气恢复”，原“行为半径”改为“移动限制”，原“伤害倍率”改为“科技收入倍率”；增援点原“势力”实际是“朝向”；原“路线”栏目实际是“部队组”，其列表元素是成员 UID。旧内部标识保留，避免已有 Lua 和 XML 因改名失效。

## 详情编辑规则

- 每个普通值有独立的“应用”按钮，只提交这个字段。布尔值区分未写、否、是；数字空白表示删除槽位；字符串允许写入空字符串，删除字符串用“清空”。
- 子配置显示“未写”时，展开只查看状态，点击“创建配置”才会写入。清除配置会删除整组；这些修改都可撤销。
- 普通数值列表用逗号分隔，空白删除字段，`[]` 写入真实的空列表。表和结构体列表通过添加、选中、删除条目编辑，只生成当前条目的输入框。
- 嵌套结构体内的成员不能缺省为“未写”，清空输入后应用会写零。部队基础结构的经验/编数、朝向/移动力保留等宽合并表示，日常操作优先用基础栏的分项输入；详情中的合并值有位段说明。
- 行为树运行状态、Lua 触发事件及动作队列等序列化字节仍按字节列表编辑。本轮提供字段入口和原始数据编辑，未将所有内部载荷翻译成游戏业务表单。共用树定义库继续使用专用 FlexBuffers 页面。

研究指出有符号的地图格、士气及关联索引已按对应类型处理，保留 `-1` 等有效值；建筑奖励、着火状态、加成列表、将领池等结构也按标注修正。尚未解析完整的文件继续遵守原来的只读及禁止重建规则。

## 后续研究怎么更新

这三层分别维护：

| 文件 | 职责 |
| --- | --- |
| `scripts/common/研究结构.lua` | 用已有 `editor.format.schema` 声明修订后的物理类型；在读 BTL 之前加载 |
| `fields/research-labels.json` | 59 个类型、281 个源字段的短名、说明、不确定性标记及研究快照摘要 |
| `pages/*.xml` | 页面位置、常用字段、折叠默认值、详细配置入口和重复字段排除列表 |

详情实际读取当前文档的 schema。对已接入的类型新增普通标量、表、结构体或列表，只需补 Lua 类型声明和名称目录，即可递归显示。只有新编码、特殊控件或业务操作超出现有能力时，才需要补专用处理。用户扩展字段若没有名称条目，显示“字段 N”，不会猜测名称。

维护脚本 `tools/BuildResearchLayout/generate.py` 从人工 FBS 生成类型覆盖和名称快照。先调整脚本中的短名表，再在仓库根执行：

```text
python tools/BuildResearchLayout/generate.py "战役相关文件/BTL字段相关研究结果/battle - 人工命名版.fbs"
```

原研究文件保持只读。生成结果已随源码保存，运行编辑器不需要研究资料或 Python。`update_pages.py` 是现有页面的迁移辅助脚本；日常维护直接修改 XML 即可，不必反复运行它。

可折叠分组支持嵌套：

```xml
<group id="advanced" title="高级配置" collapsible="true" collapsed="true">
  <group id="general" title="将领配置" collapsible="true" collapsed="false">
    <row label="勋章ID">
      <field id="medal" field="unit.general.medal" tip="将领使用的勋章ID" />
    </row>
  </group>
</group>
```

详细配置入口示例：

```xml
<section id="unit_details" title="部队详情" kind="details"
         bind="/6/0" resolve="unit" selection="/6/0" model="AIAgent"
         omit="2,3,5,6,10,11" labels="../fields/research-labels.json"
         collapsible="true" collapsed="true" />
```

`bind` 指向对象或对象向量；`model` 是 schema 类型；`resolve` 根据地图选择定位向量行；`selection` 根据本页列表定位，二者同时提供时列表优先。`omit` 只排除入口对象的字段 ID，子对象不继承。`labels` 相对页面 XML 所在目录解析。复制页面到用户覆盖目录时，应一起复制名称文件或调整引用路径。

对象向量详情可增加 `browse="true"`（同时保留 `resolve` 或 `selection`）。详情内会出现独立对象选择框；无外部选择时默认显示第一项。选择框显示对象编号，势力选择框与本页势力列表同步。真正没有条目时显示空状态，不会自动创建数据。阵营页的「势力详细配置」使用此选项；折叠和控件复用行为保持不变。

建筑页的「地块与地标详情」按当前地图格显示，不使用对象列表。`TriggerEvent` 是地块的附加记录，不要求包含建筑或工事；空地起火也保存在这类记录中。页面使用 `resolve="event" prepare="ensure_cell_event"`：选中已有记录的格子直接显示其字段；选中没有记录的空地，显示未配置的字段和分组。浏览、展开和切换地块不创建任何数据；第一次明确应用字段或创建子配置时，调用 Lua 动作 `ensure_cell_event`，仅补上地块 ID，再写入用户所选配置。补记录与实际修改共用一个事务和一次撤销；输入无效时整个操作回滚。只设置起火不会自动增加建筑或工事。

`prepare` 用于按地图选择定位的 `details` 栏目，需要配合 `resolve`，不能与 `browse` 同时使用。创建记录的逻辑放在 Lua，界面不假定记录字段的具体排列。自定义页面可以提供自己的准备动作，动作完成后 `resolve` 应返回当前格子的真实行号。

这份类型修订通过编辑器的 Lua 加载流程生效，不会静默改写其他程序使用的默认 schema。热加载也不会重新解释已打开的文档；更新物理类型后应重新打开原始 BTL。旧工作文档携带旧解释指纹时，应按原有兼容规则处理，不能靠改名跳过解释校验。

## 验证记录

本轮检查了 459 份原版 BTL：全部无阻断诊断读入、成功重建、再次读入且文档内容一致；原默认解释可完整处理其中 449 份。此结果验证读写一致性，不代表所有新增状态组合已在游戏内验证。

自动检查包含局部修改保留其他字段、未写/零/false/空列表、非法输入回滚、有符号值、嵌套表和结构体写回、勋章及建筑加成、新旧布局兼容；真实界面检查包含折叠高度、展开不修改文档、创建配置、列表逐项修改、地图外选择、撤销和重做。较深层详情使用简单纵向布局，避免自动尺寸表格反复测量。
